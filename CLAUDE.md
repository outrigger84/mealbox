# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this app is

A personal, single-user meal-delivery-subscription manager. It solves three pain points: (1) knowing which delivery to order for, given current stock and days already planned for eating elsewhere, (2) catching food before it expires unplanned — including flagging which meals should go in the freezer, based on an actual Breakfast/Lunch/Dinner consumption plan rather than a guess, and (3) planning which meal-slots will use a subscription meal. Ordering and delivery are treated as two distinct real-world events (log the order, then separately receipt what actually arrives) rather than one step.

This app is part of a fleet of independent apps behind nginx/PM2 on this server — see `/root/SYSTEM.md` for the shared architecture (base path, port, PM2, nginx conventions) and `/root/CLAUDE.md` for the fleet index. This file covers only what's specific to `mealbox` (port 3011, base `/mealbox`).

## Commands

```bash
npm run dev      # concurrently runs server (Express) + client (Vite)
npm run build    # vite build, output to server/public/
npm run start    # starts Express server
```

No test suite exists for this app.

## Architecture

**Server**: SQLite at `server/data/mealbox.db`.

Tables:
- `schedule_config` — single-row (`id=1`) settings: fixed weekly `delivery_weekday`/`order_by_weekday` (0=Sun..6=Sat), display-only `order_by_time`, `default_order_qty`.
- `meals` — one row per physical meal item, created only once a delivery is receipted (either via the order→receipt flow or a manual add): `delivery_date` (which batch it arrived with, denormalized rather than a separate deliveries table), `expiry_date`, `assigned_date` (still unused by any UI — the single-meal-per-day column from before the slot planner; assignment now lives on `meal_slots.meal_id` instead, see below), `eaten`/`eaten_date`, `frozen_at`/`freeze_type` (`light`/`deep` — see the freezer note below).
- `order_plans` — a logged order: `delivery_date` (expected), `planned_qty`, `received_at` (null until the delivery is receipted — this is what "pending receipt" means).
- `order_plan_items` — the expected meal names for an order plan, parsed from the pasted box-contents summary at order time. Each row tracks `received` (set during receipt) and `meal_id` (linked to the `meals` row created for it, or left null if that item didn't actually arrive).
- `non_subscription_days` — flat `date` + `reason` (`eating_out`/`self_cooking`/`other`) table, superseded by the `meal_slots` planner below. No UI writes to it any more (the old Calendar day-level flag was replaced by the slot planner) and `computeOrderNeed` no longer reads it either (see `meal_slots` note) — kept only because nothing has asked to remove it yet, same as the legacy `/calendar` route.
- `meal_slots` — the Breakfast/Lunch/Dinner planner: `date` + `meal_type` (`breakfast`/`lunch`/`dinner`) + `status` (`subscription`/`not_subscription`/`freezer`) + `meal_id` (nullable FK to `meals`, `ON DELETE SET NULL`), `UNIQUE(date, meal_type)`. Sparse by design — a day/slot with no row defaults to `subscription` (previously "undecided"; there is still no stored default-status value, it's just interpreted as `subscription` instead of a neutral unset state). Tapping a slot in the UI cycles subscription (no row) → not_subscription → freezer → back to subscription (deletes the row again), each step a `PUT /meal-slots` that either upserts a row or deletes it (status `null`) to go back to the no-row default; that clears `meal_id` too, since only a `subscription` slot can hold one. `meal_id` is deliberately a *second*, independent action (`PUT /meal-slots/meal`) from the status cycle — a week's worth of slots are "subscription" by default (to decide whether you even need to order) before any physical meal exists to fill them; picking which specific stock meal goes in a slot is optional and can happen later, or never. Picking a meal for a no-row (default-subscription) slot auto-creates the row with `status = 'subscription'` first, since `meal_id` needs somewhere to attach to.

A `freezer`-status slot *is* wired to `meals.freeze_type`: it's for planning when a deep-frozen meal will actually get eaten, so it can only take a meal with `freeze_type = 'deep'`, while a `subscription` slot can only take fresh or light-frozen stock (never deep). `PUT /meal-slots/meal` enforces this pairing server-side (400s on a mismatch), and `PUT /meal-slots` (the status cycle) also re-checks it — cycling a slot between `subscription` and `freezer` keeps its `meal_id` only if the assigned meal still matches the new status's rule, clearing it otherwise, so a slot can never end up silently holding a mismatched meal. `not_subscription` (or back to the no-row default) always clears `meal_id` regardless.

### Freezer tracking

A meal is frozen when `meals.frozen_at` is set (date frozen) with `freeze_type` `'light'` (still planned to be eaten within the current subscription cycle) or `'deep'` (not planned within this cycle — carries over). There's no "thaw" step: these meals cook directly from frozen, so the only transition from frozen is `POST /meals/:id/eat` (unchanged, works regardless of frozen state) or `POST /meals/:id/unfreeze` (a correction path for mistakes, not part of the normal flow — clears both columns, reverting to normal expiry tracking with whatever `expiry_date` it already had).

Freezing pauses expiry pressure: `computeExpiryWarnings()` and `computeFreezerCandidates()` (`server/lib/stock.js`) both exclude meals where `frozen_at` is set. `computeOrderNeed()`'s `stockAvailable` count treats a frozen meal as available regardless of whether its original `expiry_date` has passed — freezing is what preserves it past that date, so the naive `expiry_date >= today` check alone would wrongly drop it right when freezing was needed.

`freeze_type` is suggested, not enforced: `server/routes/dashboard.js` computes `suggestedFreezeType` per freezer candidate by checking whether it already has a `meal_slots` assignment on or before the current cycle's `cycleEnd` (light) or not (deep, including unassigned candidates) — see cycle math below. The Home freeze action pre-selects this but the user can override either way.

### Subscription cycles

`server/lib/schedule.js`'s `cycleBounds(scheduleConfig, today, offset)` computes a 7-day cycle. Since a meal can't be eaten the day it's delivered (same rule `computeFreezerCandidates` already used), a cycle's *usable* window is defined as the day after one delivery through the next delivery date inclusive — not the calendar week starting on delivery day. So for a Sunday delivery, the current cycle showing "Mon–Sun" is correct and intentional, not an off-by-one. Returns `{ cycleStart, cycleEnd, deliveryDate, nextDeliveryDate, orderByDate }`; `offset` steps whole cycles (each exactly 7 days) forward/back. Exposed at `GET /schedule/cycle?offset=N` (mounted on the `schedule` router, so full path `${BASE}/api/schedule/cycle`).

Dates are stored as `YYYY-MM-DD` TEXT and parsed as UTC (`new Date(str + 'T00:00:00Z')`) throughout, to avoid timezone drift — see `server/lib/dates.js` for the shared `addDays`/`daysBetween`/`todayStr` helpers.

Business logic is pure functions with no DB access, mirroring `supplement-tracker`'s `stock.js` pattern:
- `server/lib/schedule.js` — `nextDeliveryInfo()` computes the next delivery date and order-by cutoff from the fixed weekday config, rolling forward a week if the current cutoff has already passed.
- `server/lib/stock.js` — `computeOrderNeed(meals, mealSlotsByDate, enabledMealTypes, scheduleConfig, today)` counts demand (one unit per enabled meal type per day, minus explicit `not_subscription` slots — a `freezer`-status slot still counts, same demand definition as the projection panel below) until the next delivery and through the following cycle, compares against current unexpired/uneaten stock, and returns a suggested order quantity as `mealsNeededUntilDelivery`/`mealsNeededNextCycle`. `server/routes/dashboard.js` builds `mealSlotsByDate` from `meal_slots` rows in `[today, followingDeliveryDate)` for this — no longer sourced from the dead `non_subscription_days` table, and no longer a day-level count either (an earlier version counted one unit per day regardless of how many meal types were enabled, which undercounted demand once more than one meal type was on subscription — this now matches every other demand calculation in the app). `GET /dashboard` also separately reports `pendingOrder` (the `order_plans` row, if any, already logged for `delivery.nextDeliveryDate` with `received_at` still null) so the Home page can show "already ordered" instead of a stale suggestion once one exists — `computeOrderNeed` itself has no notion of a logged-but-not-yet-received order. `computeExpiryWarnings()` flags uneaten meals expiring within a few days. `computeFreezerCandidates()` matches uneaten stock (earliest-expiring first) against subscription demand — a meal already assigned (`meal_id`) to a slot is checked against that slot's own real date first; only unassigned meals then compete, greedily, for the remaining open slot-dates. This avoids a meal that's already safely assigned being mislabeled a candidate just because the greedy pass would otherwise have matched a different meal to that date first. Demand isn't just explicit `subscription`-status rows: `server/routes/dashboard.js` builds the slot list it passes in by combining those with a generated entry (`meal_id: null`) for every `(date, enabled meal_type)` combo in `[today, furthest relevant stock expiry date]` that has no row at all, matching the no-row-defaults-to-subscription convention above — bounded to that horizon since no slot beyond the furthest expiry could ever affect matching anyway.

Routes, mounted per-resource at `${BASE}/api/<resource>`:
- `/schedule` — `GET/PATCH /` (the singleton config row), `GET /cycle?offset=N` (see subscription cycles below).
- `/meals` — `GET /` (filters: `?eaten=0`/`?eaten=1`, `?unassigned=1` — means "not eaten and not linked from any `meal_slots.meal_id`", not the old `assigned_date` check — and `?frozen=1`, combinable e.g. `?frozen=1&eaten=0`), `POST /` (single manual add — for a meal not from a logged delivery), `POST /batch` (bulk-add with a shared `delivery_date`/`expiry_date`, kept for scripting/back-compat but the UI no longer surfaces it directly), `PATCH /:id`, `POST /:id/eat`, `POST /:id/uneat` (undo — clears `eaten`/`eaten_date`, does not touch freeze columns), `POST /:id/freeze` (`{freeze_type}`, sets `frozen_at`/`freeze_type`), `POST /:id/unfreeze` (clears both), `DELETE /:id`.
- `/order-plans` — `GET /` (add `?pending=1` for orders awaiting receipt), `GET /:id`, `POST /paste` (log an order: `{delivery_date, names}` from the parsed box-contents paste — creates/updates the order plan and its `order_plan_items`), `POST /:id/receipt` (`{default_expiry_date, items:[{id, received, expiry_date?}]}` — for each received item, creates the actual `meals` row using its expiry override or the default, and stamps `received_at`), plus plain `POST /`/`PATCH /:id` for manual order-plan edits.
- `/non-subscription-days` — `GET /?start=&end=`, `POST /`, `DELETE /:id`. Backend only now — no UI writes to this (see `meal_slots` note above).
- `/meal-slots` — `GET /?start=&end=` (sparse list — only non-default-subscription rows exist — joined with `meals` for `meal_name`/`meal_expiry_date`), `PUT /` (`{date, meal_type, status}`; `status: null` deletes the row, resetting to the default `subscription` status and clearing any `meal_id`), `PUT /meal` (`{date, meal_type, meal_id}`; `meal_id: null` clears it; auto-creates a `subscription` row if none exists yet, 400s only if an existing row's status isn't `subscription`/`freezer`; assigning a meal already linked elsewhere silently unlinks it from its old slot first, since a physical meal can only fill one).
- `/dashboard` — `GET /`: the aggregated payload (`nextDeliveryInfo` + `computeOrderNeed` + `computeExpiryWarnings` + `pendingReceipts` + `pendingOrder` + freezer fields) the Home page loads. `pendingReceipts` is any order plan whose delivery date has passed but hasn't been receipted; `pendingOrder` (see the `computeOrderNeed` note above) is the one, if any, already logged for the *upcoming* delivery and not yet received. `computeFreezerCandidates` output is split in two: `freezerCandidates` is only candidates that ARE assigned to a real `meal_slots` row whose date doesn't fit their usable window — a specific, named problem. A candidate with no real assignment came out of `computeFreezerCandidates`'s generic capacity-matching pool, which only knows a *count* needs freezing, not *which* meal — any unassigned stock item is equally likely to be "the one," so naming an arbitrary N of them (e.g. by id order) would misrepresent that as a decided outcome. Those instead surface as `unallocatedFreezerPool` (every uneaten, unfrozen, unexpired meal with no real slot assignment at all — a superset of the ones that must actually be frozen) plus `needFreezingCount` (how many of that pool need it), letting the Home page show "N of these M will need freezing" and leave which specific ones to the user. Each freezer-related meal in both lists is annotated with `suggestedFreezeType` (see freezer tracking below). `GET /projection?periods=N`: the Calendar page's rolling Demand/Supply/Surplus/freezer-stock numbers for cycles `0..N-1` (offset 0 = current cycle), chained — each period's `max(0, surplus)` becomes the next period's `freezerStockAtStart`, since you can order several periods ahead and a future period's freezer supply depends on every period between now and then. `demand` = every enabled-meal-type slot in the cycle minus explicit `not_subscription` ones (a `freezer`-status slot still counts as demand — it needs a meal too, just sourced from stock rather than a fresh order, and which slot uses which source is a separate, later decision). `mealsDelivered` is always `default_order_qty` for every period (a future period hasn't actually been ordered yet, so there's nothing more accurate to use). The chain used for `supply`/`surplus` starts at `priorFreezerStock` — real deep-frozen meals with `frozen_at` *before* the current cycle's `cycleStart` — not at the full real current deep-freeze count: the current cycle's `demand` is already spoken for by `meal_slots` assignments to stock delivered before the cycle started, which this endpoint has no visibility into at all, so a meal frozen *during* the current cycle is presumed to already be explained by this cycle's own `mealsDelivered`-vs-`demand` accounting — folding it into supply on top of that would double-count it against demand it was never meeting. A meal frozen before the cycle began can't be explained that way, so it's added as genuine additional reserve (this is how older, unconsumed deep-freeze stock still gets "looked back" into the projection instead of silently vanishing from it). Period 0's *reported* `freezerStockAtStart` is still the full real count (so it matches Inventory), separate from what feeds the chain. Only meaningful forward from today — the Calendar page falls back to a simpler, non-chained estimate for a past cycle.
- `/calendar` — `GET /?start=&end=`: legacy per-day `{date, assignedMeal, isNonSubscriptionDay, nonSubscriptionDay}` endpoint from the pre-slot-planner Calendar. No longer called by any page; kept only because nothing has asked to remove it yet.

**Client**: plain `react-router-dom`, TanStack Query, Tailwind (same CSS-var theme convention as `supplement-tracker`/`reno-manager`, amber/orange accent). `client/src/api/client.js` uses the `makeEntity(slug)` CRUD factory pattern from `reno-manager`. Pages: `Home` (dashboard/reminders — order-need banner, a freezer-candidates card for meals with a specific known-bad slot assignment, a second card for the unallocated freezer pool ("N of these M will need freezing — pick which," each with a light/deep Freeze action), expiry warnings, and a banner linking to Deliveries when something needs receipting — the mobile landing screen), `Deliveries` (two tabs: **Log order** — paste the box-contents summary from the ordering site, parsed client-side by `client/src/lib/parseBoxPaste.js` into meal names via `POST /order-plans/paste`; **Receive delivery** — pick a pending order plan, check off what actually arrived, set a default expiry date with per-item override, `POST /order-plans/:id/receipt`), `Inventory` (four filter tabs — All, Unassigned, Freezer, Eaten; the "Eaten" button is always labeled, not icon-only, after a user marked 10 real meals eaten by accident thinking it meant something else; the Eaten tab lists consumed meals with an Undo action calling `POST /:id/uneat` for exactly this kind of correction; the Freezer tab groups stock into Light/Deep sections with Eaten/Remove-from-freezer actions; manual single-meal add for ad-hoc entries — bulk entry lives in Deliveries now), `Calendar` (cycle-based Breakfast/Lunch/Dinner slot planner, one 7-day cycle at a time with prev/next navigation and a header showing the cycle's delivery/order-by dates — a slot defaults to subscription, tap to cycle subscription → not_subscription → freezer → back to subscription; a collapsible "Order-decision stats" panel shows Demand/Delivered/Freezer stock/Surplus for the viewed cycle (current cycle or forward: `GET /dashboard/projection`, chained across periods since you can order several ahead; a past cycle instead shows a simpler non-chained same-cycle estimate — see the `/dashboard` route note above), and a collapsible "Mark a trip away" date-range form flags whole days off in one go), `Settings` (edit the weekly schedule). `Layout` renders a sidebar nav on desktop and a bottom-tab nav on mobile — the app is used mostly from a phone day-to-day.

Calendar rows show the cycle chip plus, for a `subscription` or `freezer` slot, a secondary "Pick meal" control (or the assigned meal's name, tap to reopen the picker; the X on that pill clears it) that opens an inline list filtered to the matching pool — fresh/light-frozen stock for `subscription`, deep-frozen only for `freezer` (`client/src/pages/Calendar.jsx` filters the same `unassigned=1` list client-side by `freeze_type`; the server independently enforces the same rule on assignment, see the `meal_slots` note above). Each option shows a warning icon if `!frozen_at && expiry_date < date`, i.e. it'll already be expired by the day being planned — frozen meals are exempt regardless of light/deep, same as Home's expiry warnings, since freezing is what pauses expiry pressure.

Picking a flagged option runs `handlePick()`: it `window.confirm()`s whether to freeze the meal first; on yes, `POST /meals/:id/freeze` with `freeze_type: 'light'` (light, not deep — this only ever fires from the `subscription` pool, which can't take deep-frozen) runs before the normal assign call, so the freeze is committed before the slot references it. The assigned-meal pill itself is colored to match: blue (`bg-sky-100`) with a snowflake when the linked meal has a `freeze_type` (the `meal-slots` routes join `meals.freeze_type AS meal_freeze_type` for this), the normal accent color otherwise — mirroring the picker's and the status-cycle chip's freezer coloring. This is deliberately a separate action from the status cycle.

`parseBoxPaste.js` expects the site's repeating `<meal name>x1<calories> kcal / <protein>g Protein` pattern (observed on simmereats.com's box-contents summary) with no separator between entries — if the ordering site's format ever changes, that regex is the only place to update; it's deliberately isolated from the rest of the order-logging flow.

## Scope boundaries (deliberate)

Manual data entry only — no live provider API integration, just paste-and-parse of a manually copied page snippet. One fixed weekly delivery/order-by cadence — no multiple concurrent subscriptions or irregular schedules. No auto-prioritization of which meal to eat — expiry info is surfaced on Home/Inventory/Calendar, the user still picks. No push notifications — "reminders" means the Home dashboard on load. No auth (single user).
